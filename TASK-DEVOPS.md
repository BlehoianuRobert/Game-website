# DevOps & Infrastructure — Hackathon Challenge

**Builders Lab Hackathon 2026**
**Owner: DevOps Engineer**

---

## 1. Context and objectives

This task simulates building a real production-ready cloud infrastructure, end-to-end, for the gaming platform that the other engineers (API, CMS, QA) are building. You do not depend on your teammates' progress: you start from your own simple service called Vector API (a minimal Python app provided in `devops/app/`) and run it through the entire cloud infrastructure pipeline. If your team's backend API is ready later, you can swap it in as a bonus.

### What we evaluate

* **Infrastructure Initialization** — Correct configuration of base virtual machine, network ports, and dependencies.
* **Infrastructure as Code (IaC)** — Writing clean Terraform configuration to manage a stateful cloud database.
* **Containerization** — Implementing an optimized Dockerfile adhering to layer caching best practices and structural validation.
* **Practical Kubernetes & Package Management** — Configuring local tracking charts via Helm and automated service scaling policies (HPA).
* **CI/CD Pipelines** — Creating an automated workflow that runs your unit tests, scans your code, builds your Docker images, and automatically deploys them to the cluster.
* **Load Testing & Observability** — Analyzing systems behavior under traffic saturation and drawing insights from telemetry systems.

### Critical Safety Rule

* **No hardcoded secrets or passwords in Git.** All credentials must use environment variables, Helm values injected at runtime, or Kubernetes Secrets.

## 2. Mandatory requirements

### 2.1 Base EC2 Setup (Manual Task)

Using the free AWS account created prior to the hackathon, you must create a virtual machine manually through the AWS Console or AWS CLI. This machine will serve as your primary orchestration plane and target hosting cluster.

* **Instance Type Recommendation:** `m7i-flex.large`
* **Operating System:** Ubuntu 26.04 LTS
* **Storage:** 20 GB HDD
* **Network Configuration:** Must assign a Public IP.
* **Security Group:** Open port 22 (SSH), port 80 (HTTP), and port 443 (HTTPS) to enable remote connectivity and ingress exposure.
* **Key Pair:** Set up a valid SSH Key Pair to securely connect to the node. 

### 2.2 Kubernetes Cluster Setup

Once connected to the EC2 instance, execute the provided idempotent bootstrap script to install the foundational developer utilities. This script automatically installs:

* **Docker Engine**
* **kind** (Kubernetes in Docker)
* **kubectl** (Kubernetes CLI)
* **Helm** (Kubernetes Package Manager)
* **Terraform** (Infrastructure as Code CLI)
* **k6** (Performance & Load Testing CLI)

* Make the script executable and run it:

```bash
chmod +x devops/bootstrap.sh
./devops/bootstrap.sh

```

* Instantiate the cluster using the provided network mapping schema config file:

```bash
kind create cluster --name hackathon --config devops/kind-config.yaml

```
> **Note:** The included `kind-config.yaml` file is explicitly customized to map incoming host ports `80` and `443` directly into the cluster control plane to facilitate simple Ingress controllers and routing configurations.

* After initializing your cluster environment, execute standard validation routines to confirm cluster operational health:

```bash
# Verify cluster configuration status
kubectl cluster-info

# List running cluster nodes 
kubectl get nodes

```

### 2.3 Cloud Database Provisioning via Terraform

Instead of hosting MySQL directly inside the Kubernetes cluster, you must configure a persistent, managed relational database service using Infrastructure as Code.

* Use **Terraform** inside the `devops/terraform/` directory to automatically provision an **AWS RDS MySQL** database.
* The infrastructure variables, connection strings, and endpoints generated by Terraform must be injected into the application runtime without committing credentials to Git.
* You can authenticate Terraform either by manually configuring AWS credentials for an IAM user with administrative permissions on the EC2 instance, or by attaching an equivalent IAM role/profile directly to the EC2 instance.

### 2.4 Core Cluster Platform Components

You must install all cluster infrastructure platform components using Helm. To maintain complete control over chart tracking and reproducibility, **you must first download the Helm charts locally into their corresponding pre-created subdirectories inside `devops/k8s/` and install them from those local paths**

* **Nginx Ingress Controller:** This component handles traffic entering the cluster from your public EC2 address.
* **Prometheus:** Collects and stores real-time performance metrics and resource usage data from your cluster and applications.
* **Grafana:** Provides a visual dashboard to query, analyze, and monitor the metrics collected by Prometheus.
* **Metrics Server:** Provides real-time CPU and memory usage metrics from Kubernetes nodes and pods, enabling features such as Horizontal Pod Autoscaling (HPA) and resource monitoring.
* **Custom Application Chart:** Create a custom Helm chart for the Vector API inside `devops/helm/vector-api/`.

### 2.5 Application Containerization

Develop a production-ready container blueprint for the Vector API application located inside `devops/app/`. The provided files are:

* **`vector_api.py`**: A Flask-based REST microservice exposing two endpoints:
* `GET /health`: Liveness probe for monitoring agent compliance.
* `POST /vector`: Accepts a numerical array via JSON, calculates metrics (count, magnitude, normalization), and logs transaction history to a database backed by SQLAlchemy (configured via the `DB_URL` environment variable).
* **`requirements.txt`**: Defines the application runtime dependencies with version-pinned major releases for Flask, SQLAlchemy, Gunicorn, and MySQL connectors.
* **`test_unit.py`**: A clean PyTest automation file testing basic routing logic, error thresholds, array validation matrices, and endpoint integrity against an ephemeral in-memory SQLite backend.

Starting from these files you will need to:

* Create a `Dockerfile` that packages the Flask application and uses the Gunicorn WSGI server.
* Optimize the execution layers: structure dependencies and application layers to take full advantage of Docker layer caching, reducing pipeline build times.

### 2.6 Self-Hosted GitHub Runner & CI/CD Pipeline

To enable your automation pipeline to directly interact with the local Kubernetes cluster and build resources on the EC2 host machine, you must configure a GitHub Actions Self-Hosted Runner on the same instance.

* Install and register a GitHub Actions Self-Hosted Runner directly on the EC2 instance. The required setup commands and registration steps will be provided during the hackathon when needed.
* Create a workflow configuration file inside the `.github/workflows/` directory that automatically executes on every push to the `main` branch.
* **Pipeline Stages:**
1. **Run Unit Tests:** Execute the unit tests located in `devops/app/tests/test_unit.py` via pytest in a virtual environment, before proceeding to build tasks.
2. **Build Image:** Compile the Docker container image directly on your EC2 instance.
3. **Load Image:** Load the image in the kind cluster.
4. **Deploy App:** Deploy or update the application inside the kind cluster using your custom Helm chart, ensuring the deployment reflects the latest committed changes.

#### Exposing Endpoints:

* **Vector API Application:** Must be exposed and publicly accessible at the root route: `http://<your_ec2_public_ip>/`

### 2.7 Auto-Scaling (HPA) & Load Testing

The application infrastructure must dynamically scale under increased workload conditions to maintain availability, responsiveness, and system stability under traffic pressure.

* Add a **Horizontal Pod Autoscaler (HPA)** configuration to the custom Vector API Helm chart to enable automatic scaling of deployment pods based on increased resource usage.
* Write a load testing script using **k6** and place the file inside the `devops/load-tests/` directory.
* The level of incoming traffic should be high enough to activate the HPA scaling rules, prompting Kubernetes to expand the number of running application instances.
* You must make a screen capture of this scaling behavior from the Grafana dashboards and present it during the evaluation.

## 3. Bonus Points

If you complete the core requirements early, implement the following advanced infrastructure extensions to maximize evaluation scoring:

### 3.1 Headlamp Dashboard Installation

* Download the **Headlamp** Helm chart into `devops/k8s/headlamp/` and install it inside your kind cluster.

### 3.2 Automated Data Lifecycle Management via CronJob

* Create a native **Kubernetes CronJob** manifest located inside `devops/k8s/cronjobs/`.
* The job must execute periodically to connect to your AWS RDS MySQL instance and run a cleanup database script that purges logged events older than 10 minutes.

### 3.3 Container Security Scanning

* Extend your `.github/workflows/` CI/CD pipeline code to include a security scanning stage.
* Integrate a tool like **Trivy** to scan your compiled Vector API Docker image for CVE vulnerabilities before executing the application rollout inside your cluster.

## 4. Demo — what must be shown

During the final 5-minute technical demonstration, you must show the live system operating end-to-end:

1. **Pipeline Execution:** Trigger a push to the `main` branch. Show the GitHub Actions runner on the EC2 machine executing unit tests, compiling the Docker image, and executing a safe deploy.
2. **External Application Access:** Send a browser or curl request directly to `http://<your_ec2_public_ip>/` from outside the machine to show the application responding to queries.
3. **Managed Database Persistence:** Verify that the application records data updates into your remote AWS RDS instance initialized by Terraform.
4. **Load Test Scaling:** Present a screenshot of a Grafana dashboard capturing how the application scaled up in response to the load test traffic.
5. **Bonus Demos (If implemented):** Show how Headlamp provides operational visibility, display logs from a successful container security scan, or present logs confirming that the data lifecycle cleanup CronJob executed successfully.
